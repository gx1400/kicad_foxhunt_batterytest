- [ ] Continue schematic capture for the [controller/peripheral platform](controller_platform.md) — the VRAW soft-latch and PCF8563 RTC are done; GPS, SD card, EEPROM, audio/PTT path, RF power sensing, status LEDs, and TX-safety timeout are still planning-only.
- [ ] Once the controller section has real current draws, re-verify the existing 5V/2A and 3.3V/1A [regulation](regulation.md) budget still covers it.
- [ ] Design a power-*off* path for the VRAW soft-latch — the button/RTC-interrupt/MCU-latch circuit currently only powers the system *on*; shutdown today only happens if firmware voluntarily releases its own GPIO48/Q6 latch-hold, no hold-to-shutdown UX and no hardware-guaranteed force-off if firmware hangs. Leading option: a second pole on the power button (DPST, not the existing SPST SW3), landing on IO38 (already reserved for this — see `esp32s3_pinout.md`), so firmware can time a long-press and release the latch — cheaper on standby current than tapping the existing VRAW-swing wake node with a divider. Still open: whether a firmware-independent hardware force-off is worth the added complexity — leading option there is reusing the *spare half* of the 74HC123 dual monostable already planned for TX-safety timeout (§ TX safety in controller_platform.md), triggered directly by the button's second pole, RC-timed longer than the software hold threshold — zero added GPIO or parts cost.
- [ ] Add an I2C GPIO expander (PCF8574/PCA9555-class, address `0x20`–`0x27`, shares the existing RTC/fuel-gauge/EEPROM bus) to drive the TX-active and heartbeat status LEDs — both are slow/no-timing-requirement signals, freeing IO3 and IO39 back to spare (see `esp32s3_pinout.md`). The WS2812/RGB status LED stays on its own native GPIO regardless (needs real serial-protocol timing, not a static register).
